# Family_tree 技术栈设计

## 1. 最终结论

本项目重构后的最终技术栈定为：

```text
前端框架：Vue 3 + Vite
图渲染交互：AntV G6
主族谱布局：ELK.js layered layout
后端框架：FastAPI
数据库：Neo4j
数据库驱动：Neo4j Python Driver
图数据模型：Person + FamilyUnit + 关系元数据
文件存储：本地 uploads 起步，后续可迁移对象存储
部署：Docker Compose + Nginx
```

核心原则：

- Neo4j 负责存储和查询真实亲缘关系。
- ELK.js 负责计算主族谱视图的稳定二维布局。
- G6 负责图画布的缩放、拖拽、选中、高亮、交互状态。
- Vue 负责页面组织、表单、弹窗、侧栏和业务状态。
- FastAPI 负责权限、接口、数据清洗、关系校验和视图数据组装。

这套组合是当前目标下的工程最优解：普通用户看得懂、查得快，管理员改得清楚，后续关系复杂化也能承接。

## 2. 为什么数据库选择 Neo4j

族谱不是普通二维表，也不是严格树，而是关系图。

当前 MySQL 模型使用 `father_id` 和 `mother_id` 表示父母关系，适合早期版本，但当需求扩展到配偶、再婚、收养、继亲、资料来源、可信度、两人关系路径时，关系型表会不断膨胀，后端也会被迫把数据取出来再临时构图。

Neo4j 更适合本项目的原因：

- 人物天然是节点，亲缘、婚姻、收养、资料来源天然是关系。
- Cypher 适合查询祖先、后代、亲缘路径、两人最短关系链。
- 关系本身可以携带属性，例如关系类型、顺序、时间范围、可信度。
- 后端不需要每次把全库搬到 NetworkX 才能做基础图查询。
- 后续做异常检测更直接，例如循环祖先、重复父母、孤立节点、跨支婚姻。

需要明确：Neo4j 不负责网页拖拽交互。它解决的是“关系事实如何存、如何查”，前端显示和拖拽仍由前端图形库完成。

## 3. 为什么前端选择 ELK.js + G6

族谱前端真正困难的不是画节点，而是布局。

如果只用普通树布局，遇到夫妻、多子女、再婚、同父异母、收养、跨分支关系，很容易出现线条交叉、层级混乱、分支挤压。主族谱图需要的是“分层、稳定、尽量少交叉、可解释”的布局。

ELK.js 的定位是布局引擎，适合分层图和复杂连线路由。它负责把后端返回的图数据计算成坐标和边路径。

G6 的定位是图渲染与交互引擎，适合缩放、拖拽、选中、节点状态、边状态、画布事件。它负责把 ELK.js 计算出的结果渲染出来，并承载用户交互。

最终分工：

```text
Neo4j -> FastAPI -> GraphViewDTO -> ELK.js -> G6 -> Vue 页面
```

不建议继续在 `App.vue` 中手写布局、绘制、拖拽、业务状态。重构后必须拆出独立画布模块。

## 4. 图数据模型

核心模型不要只做 `Person -> Person` 的父子关系，而要引入 `FamilyUnit`。

### 4.1 节点

`Person` 表示人物：

- `personId`
- `name`
- `gender`
- `birthDate`
- `deathDate`
- `isAlive`
- `avatar`
- `occupation`
- `address`
- `biography`
- `motto`
- `achievements`
- `createdAt`
- `updatedAt`

`FamilyUnit` 表示一次家庭单元：

- `familyUnitId`
- `type`: marriage, partner, single_parent, unknown_parent, adoptive
- `startDate`
- `endDate`
- `displayOrder`
- `createdAt`
- `updatedAt`

`User` 表示账号：

- `userId`
- `username`
- `passwordHash`
- `email`
- `realName`
- `isAdmin`
- `isActive`
- `createdAt`

`Media` 表示头像、照片、文档：

- `mediaId`
- `url`
- `type`
- `filename`
- `createdAt`

`Source` 表示资料来源：

- `sourceId`
- `title`
- `type`
- `description`
- `createdAt`

### 4.2 关系

`(:Person)-[:PARTNER_IN]->(:FamilyUnit)`

表示某人属于某个家庭单元。一个人可以属于多个家庭单元，用于表达再婚、多任配偶、单亲家庭等。

`(:FamilyUnit)-[:HAS_CHILD {birthOrder, relationKind}]->(:Person)`

表示家庭单元拥有某个孩子。`relationKind` 可取 biological、adoptive、step、unknown。

`(:Person)-[:PARENT_OF {side, relationKind, certainty}]->(:Person)`

可选冗余关系，用于提升路径查询和称谓计算效率。`side` 可取 father、mother、parent。

`(:Person)-[:SPOUSE_OF {startDate, endDate, order}]-(:Person)`

可选冗余关系，用于快速查询配偶。

`(:User)-[:BOUND_TO]->(:Person)`

表示账号绑定到族谱人物。

`(:Person)-[:HAS_MEDIA]->(:Media)`

表示人物拥有头像、照片或相关文件。

`(:Source)-[:SUPPORTS]->(:Evidence)`

表示资料来源支持某条人物或关系信息。Neo4j 关系不能直接指向关系时，用证据节点承接。

### 4.3 为什么必须有 FamilyUnit

`FamilyUnit` 是本次重构的关键。

没有它，夫妻到孩子会变成两条甚至多条直接边，前端很容易出现重复线和交叉线。引入 `FamilyUnit` 后，前端可以把家庭单元画成一个很小的汇聚点或隐形节点：

```text
父亲 ----\
         FamilyUnit ---- 子女 1
母亲 ----/              ---- 子女 2
                         ---- 子女 3
```

它能自然支持：

- 夫妻共同子女
- 单亲子女
- 未知父母
- 再婚家庭
- 收养关系
- 同父异母、同母异父
- 配偶顺序和子女出生顺序

## 5. 后端技术设计

后端保留 FastAPI，但数据访问层要从 SQLAlchemy 模型逐步切换到 Neo4j repository。

建议目录结构：

```text
after/app/
  main.py
  config.py
  neo4j.py
  repositories/
    person_repository.py
    family_repository.py
    graph_repository.py
    user_repository.py
  services/
    graph_view_service.py
    relation_path_service.py
    relationship_validation_service.py
    auth_service.py
  routers/
    persons.py
    graph.py
    relationships.py
    auth.py
  schemas/
    person.py
    graph.py
    relationship.py
    user.py
```

核心后端职责：

- 封装 Cypher，不让路由层直接拼查询。
- 输出前端稳定的 `GraphViewDTO`。
- 校验关系合法性。
- 计算两人关系路径。
- 生成中文称谓结果。
- 检测异常数据。
- 控制权限。

建议新增主要接口：

```text
GET    /api/graph/focus/{personId}
GET    /api/graph/branch/{familyUnitId}
GET    /api/graph/relation-path?from={personId}&to={personId}
POST   /api/persons
PATCH  /api/persons/{personId}
POST   /api/family-units
POST   /api/relationships
PATCH  /api/layout-hints
GET    /api/admin/graph-issues
```

## 6. 前端技术设计

前端保留 Vue 3 + Vite，重构重点是把族谱画布从大组件中拆出来。

建议目录结构：

```text
front/src/
  api/
    graph.js
    persons.js
    relationships.js
    auth.js
  views/
    FamilyGraphView.vue
    AdminManageView.vue
  components/
    graph/
      FamilyGraphCanvas.vue
      GraphToolbar.vue
      PersonNode.vue
      FamilyUnitNode.vue
      PersonDetailDrawer.vue
      RelationPathPanel.vue
      MiniMap.vue
    admin/
      PersonEditor.vue
      RelationshipEditor.vue
      GraphIssuePanel.vue
  composables/
    useGraphData.js
    useGraphLayout.js
    useGraphInteractions.js
    useRelationPath.js
```

前端分层：

- API 层：只负责请求。
- 数据适配层：把后端 DTO 转换成 ELK/G6 可用结构。
- 布局层：调用 ELK.js，产出坐标和边路径。
- 渲染层：使用 G6 渲染节点和边。
- 交互层：处理缩放、拖拽、选择、搜索、定位、关系创建。
- 业务 UI 层：详情侧栏、编辑表单、关系查询、异常提示。

## 7. 拖拽设计

拖拽不应该只有一种语义。

### 7.1 观察拖拽

用于普通用户临时挪开节点，看清线条。

- 不写数据库。
- 可回弹或一键恢复布局。
- 不改变亲缘关系。

### 7.2 排序拖拽

用于管理员调整同辈、配偶、分支顺序。

- 写入 `birthOrder`、`displayOrder`、`branchOrder`。
- 保存后重新执行布局。
- 不保存绝对坐标。

### 7.3 建关系拖拽

用于管理员创建关系。

- 从人物端口拖到目标人物或家庭单元。
- 松手后弹出确认表单。
- 明确选择关系类型。
- 后端校验后再写入 Neo4j。

不要根据“拖到了某个视觉位置”自动推断亲缘关系。

## 8. 视图类型

用户端默认视图：

- 中心人物谱系图
- 关系路径图
- 分支后代图
- 人物详情侧栏

管理员端视图：

- 人物表格
- 图谱编辑器
- 全图探索图
- 异常关系检测
- 批量导入导出

全图探索图只给管理员使用，不作为普通用户默认入口。完整全图天然容易混乱，不能用它承载日常浏览。

## 9. 迁移策略

### 第 1 步：语义冻结

先确认关系规则：

- 是否允许多任配偶。
- 是否允许养父母、继父母。
- 是否允许未知父母。
- 是否需要记录婚姻时间。
- 是否需要记录资料来源和可信度。
- 同名人物如何去重。
- 是否需要 GEDCOM 导入导出。

### 第 2 步：Neo4j 原型

- Docker Compose 增加 Neo4j。
- 建立唯一约束和索引。
- 准备少量模拟数据。
- 验证 Person + FamilyUnit 模型。

### 第 3 步：后端新接口

- 引入 Neo4j Python Driver。
- 新建 repository/service 层。
- 实现 `focus graph` 和 `relation path`。
- 保持旧接口短期兼容。

### 第 4 步：前端新画布

- 新建 `FamilyGraphCanvas.vue`。
- 接入 ELK.js 计算布局。
- 使用 G6 渲染节点和边。
- 恢复搜索、定位、详情、缩放。

### 第 5 步：管理员能力

- 人物管理。
- 关系编辑。
- 排序拖拽。
- 异常检测。

### 第 6 步：正式迁移

- 从 MySQL 导出人物和关系。
- 清洗数据。
- 导入 Neo4j。
- 验证账号、头像、族谱关系。
- 切换生产接口。

## 10. 风险控制

主要风险：

- 全量族谱无法保证二维无交叉显示。
- 关系语义如果前期不定，Neo4j 模型会返工。
- 前端如果继续堆在一个大组件里，后续维护困难。
- 管理员拖拽如果不加确认，容易误改真实关系。

控制方式：

- 使用多视图，而不是一张全图承载所有信息。
- 数据模型先定 `FamilyUnit`。
- 布局和渲染拆层。
- 拖拽只保存排序或明确关系，不保存随意坐标。
- 所有关系变更进入后端校验。

## 11. 最终拍板

最终采用：

```text
FastAPI + Neo4j Python Driver + Neo4j
Vue 3 + Vite + ELK.js + AntV G6
Person + FamilyUnit + Relationship metadata
中心谱系图 + 关系路径图 + 分支图 + 管理员探索图
```

这是当前项目在“用户易读、查询高效、管理员易管、关系可扩展”四个目标之间最平衡的方案。
